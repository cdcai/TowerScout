## 1 · Verdict

**The memo's factual claims all verified. Its recommendation is correct: do not publish release assets under `v0.1.0`; promote the fix and release as `v0.1.1`.** This review adds three things the memo could not:

1. **The underlying issue is systemic and latent, not machine-specific — but it is also not a `v0.1.0` regression.** `scripts/lib/TowerScoutCompose.ps1` is byte-identical between `v0.1.0-rc7.1` and `v0.1.0`, so every RC ever shipped has the same host-drift exposure. The compose files interpolate **16 variables from the process environment with precedence over the package `.env`**, three of them identity/security-critical. The trigger requires a pre-polluted host shell, so fresh pilot machines are unaffected — but two realistic populations are exposed (§3).
2. **The validation gate itself is spoofable at the tag.** The D4 harness reads `image_digest` from the readiness JSON, which is a compose-injected env var from `.env` — under a host `TOWERSCOUT_IMAGE` override, readiness would report the pinned digest while a different image runs. §5 adds an engine-level digest cross-check to close this independently of the launcher fix.
3. **The launcher fix is aimed at exactly the right layer, but it is currently uncommitted and unpushed — it has never been seen by CI or a second reviewer.** Pushing it for review is the gating next step; §5.1 is the review checklist.

The published CPU/CUDA images and the rebuilt packages are sound for their intended state: the Developer's clean-host Podman and Docker CPU validations, the digest pinning, and this review's independent GHCR digest checks all agree. This is a release-identity and provenance decision, not a product-safety emergency.

## 3 · How widespread is the problem really?

**Mechanism (verified in source at the tag):** `compose.yaml` (and the GPU overlays) interpolate `${VAR:-default}` for 16 variables. Compose resolves these from the **process environment first**, then the package `.env`. The launcher inherits the parent shell's environment and does not sanitize it: `Initialize-TowerScoutEnvFile` only creates `.env` from the template, and the existing guard `Assert-TowerScoutPackageEnvImageMatch` (TowerScoutCompose.ps1:207) validates **file-vs-file** (`.env` against `.env.example`) — it never looks at the process environment, which is the layer that actually wins.

**The three critical variables:**

- `TOWERSCOUT_IMAGE` — a host value silently replaces the digest-pinned image. **And the readiness gate cannot catch it**: `ts_runtime.py` reports `version.image_digest` from the `TOWERSCOUT_IMAGE_DIGEST` env var, which still comes from `.env` (a polluted host rarely sets the digest var too). The archived D4 harness summarizes `image_digest = $ready.version.image_digest` — so validation would print the pinned digest while exercising a different image. This is the sharpest finding of this round.
- `REQUESTS_CA_BUNDLE` / `SSL_CERT_FILE` — a host **Windows path** leaks into the Linux container where it does not exist; `webapp/ts_tls.py` treats these as first-class TLS configuration, so provider validation and geocoding fail with TLS-category errors. This reproduces exactly the symptom class the TLS-repair subsystem exists for — misleading triage toward "network inspection" when the cause is env leakage.
- `TOWERSCOUT_ALLOW_INSECURE_TLS` — a host value of `1` would silently disable provider TLS verification for a packaged launch. No evidence anyone has such a value set; noted because it is in the same override class.

**Exposed populations (honest sizing):**

1. **Developer/support machines with TowerScout residue** — `TOWERSCOUT_IMAGE=towerscout:local` is classic local-build residue. This is what bit the packaging workstation.
2. **Managed workstations with persistent CA-bundle env vars** — common on TLS-inspected networks where earlier tooling setups exported `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`. The pilot audience's machine class overlaps this population, and the Task-088 log independently recorded the same two vars breaking local `test_config.py` runs on 2026-07-08 — a second real-world data point.
3. **Fresh pilot machines** — unaffected; nothing sets these vars.

**Lineage:** the launcher file is identical from rc7.1 back through the task-084 era, so every published RC carries the same exposure. rc7.1's full validation passed because its hosts were clean — and that QA round already had to sanitize `PSModulePath` for the same class of reason. Conclusion: **latent product gap in all releases to date; real for populations 1–2; not a universal breakage; not newly introduced by this release cycle.**

**Fix-design coherence (verified against the packaged template):** the packaged `.env.example` — rewritten at package time with the pinned image, digest, and flavor — contains keys for **every** critical variable, including both CA-bundle paths and `TOWERSCOUT_ALLOW_INSECURE_TLS=0`. So the memo's fix design ("sync managed values from the package `.env` into the process environment for release-package roots") can fully neutralize host drift using values that already exist in the file, and it composes correctly with the TLS-repair flow, whose documented behavior is to write the repaired bundle path *into* `.env` (the `.env` stays the source of truth either way).

## 4 · Options assessment

**Option C / memo recommendation (`v0.1.1` from fixed source) — AGREED.** The costs are small (one review cycle, ~1h of image builds, ~30m packaging, a bounded re-validation) and the timeline still fits the 07-10 deliverable. The benefits are exactly the project's own recorded invariants.

**Option A (retag/rebuild `v0.1.0`) — reject.** Even though the tag is hours old and asset-less: (a) the two published GHCR image tags were built from `dfe9e6b` and carry that revision in their OCI metadata — retagging source desynchronizes them or forces republishing the same image tag names, which is worse; (b) CI runs and at least two workstations have already fetched the tag, and stale local tags do not auto-update on fetch — this repo has already lived through exactly that confusion with the 2025 stale `v0.1.0`; (c) Task-089's recorded invariant says the meaning of `v0.1.0` must not silently change; (d) clean `SOURCE.txt`/tag provenance is part of the AGPL story at handoff.

**Option B (publish assets under `v0.1.0` anyway) — reject, with one honesty note.** A `v0.1.0` release would not be *unsafe* for clean-host users — it equals rc7.1's exposure plus all the PR #46 fixes. The correct objections are provenance (the behavior we now trust depends on a fix absent from the tagged source) and quality (knowingly shipping a fixed-in-hand launcher gap). Frame it that way in any release-notes history; do not let the record imply the images were broken.

**Memo Option 3 (hold everything)** collapses into Option C given the timeline fits; holding adds delay without adding information. If the schedule slips past the 07-10 fix-forward window, the standing D5 fallback (rc7.1 promotion) remains available — noting that rc7.1 **inherits the same latent launcher gap**, which would then need to ship as a documented Known Issue alongside the F4 key-validation gap.

## 5 · Conditions and mechanics for the v0.1.1 path

### 5.1 The fix must be pushed, reviewed, and CI-validated **before** `v0.1.1` is tagged

The fix modifies the single most user-facing script in the package and currently exists only on one workstation with locally-run tests. Push it as a branch/PR into the normal flow. Review checklist for whoever reviews it (this reviewer is available):

- **Precedence semantics:** package `.env` values must override inherited process values for the managed set. All managed keys exist in the packaged `.env` (verified §3), so a sync-present-keys design is sufficient — but confirm behavior when a user has *deleted* a line from `.env` (fall back to `.env.example`? leave host value? define it explicitly).
- **Scope:** gated to release-package roots via the existing `Test-TowerScoutReleasePackageRoot`, so developer/source checkouts keep normal env-override workflows. The memo says this is the design; verify it.
- **Engine coverage:** the sync must run before compose invocation on **both** engine paths (docker compose and the podman-compose provider path) — confirm both flow through the patched function.
- **TLS-repair interaction:** after `repair-provider-tls -Apply` writes the container bundle path into `.env`, the sync must propagate that value (it should, by construction — verify with the repair test slice).
- **Windows PowerShell 5.1 compatibility** (the `.cmd` wrappers run WinPS, not pwsh).
- **No test weakening**; CI green at the merge SHA; the four locally-run slices (`test_task_074_bootstrap`, `test_import_assets_script`, `test_release_package_script`, `test_task_081_runtime_hardening`) plus `test_flask_routes.py` re-run in CI.

### 5.2 Close the verification hole independently of the fix

Add an **engine-level digest cross-check** to the validation protocol (and the harness if practical): after each cell reaches ready, compare the running container's image identity (`docker|podman inspect` → `RepoDigests`/image ID) against the pinned digest, rather than trusting readiness JSON alone. This turns the §3 spoof path into a detectable failure forever, regardless of host state. Record it as a D4 gate-1 addition.
