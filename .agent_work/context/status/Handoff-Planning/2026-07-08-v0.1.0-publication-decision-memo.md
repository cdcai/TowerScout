# TowerScout v0.1.0 Publication Decision Memo

**Date**: 2026-07-08
**Status**: Decision required before GitHub Release asset publication
**Scope**: Current `v0.1.0` tag, published GHCR image tags, rebuilt control packages, local Docker/Podman CPU validation, and pre-publication recommendations

## Executive Summary

The current `v0.1.0` tag is **not ready for final GitHub Release asset publication**.

This is **not** because the CPU image appears broken. The CPU runtime validated successfully on both Podman and Docker once the host machine's stale `TOWERSCOUT_*` and TLS CA-bundle environment overrides were removed or neutralized.

The actual blocker is release identity:

1. The public `v0.1.0` tag has already been created and pushed.
2. CPU and CUDA GHCR image tags for `v0.1.0` have already been published.
3. After those publication steps, a real package-launcher hardening issue was discovered and fixed locally in source.
4. That fix is **not part of the current public `v0.1.0` source tag or the already-published `v0.1.0` image tags**.

Because of that, publishing final GitHub Release assets under `v0.1.0` would create a provenance mismatch between:

- the public source tag
- the already-published GHCR image tags
- the current fixed local source tree
- the rebuilt package behavior we now actually trust

## What Problems Were Real Today

### Real host-environment problems

These were real, reproducible issues on this workstation:

1. Host shell exported stale `TOWERSCOUT_*` values, especially:
   - `TOWERSCOUT_IMAGE=towerscout:local`
   - related container/port/runtime values
2. Host shell exported stale TLS CA-bundle overrides:
   - `REQUESTS_CA_BUNDLE`
   - `SSL_CERT_FILE`
3. The first Docker asset-import attempt hit a `docker cp` closed-pipe failure while copying the large shapefile.

### What these problems did **not** mean

They did **not** prove that:

- the pinned CPU GHCR image is inherently broken
- the rebuilt CPU control package is inherently broken
- users downloading a clean release package would necessarily hit the same behavior

Once the host environment was cleaned and the Docker asset import was retried, the CPU package validated successfully on both Podman and Docker.

## Source Change Made After Tag And Image Publication

After the above validation work, a real launcher hardening fix was implemented locally:

- `scripts/lib/TowerScoutCompose.ps1`
- `tests/unit/test_task_074_bootstrap.py`

### What the fix does

For release-package roots, `Initialize-TowerScoutEnvFile` now synchronizes managed package environment variables from the package `.env` into the process environment, including the pinned image fields and TLS bundle settings, instead of allowing stale host-shell values to silently win.

This specifically protects packaged launches from parent-shell drift such as:

- `TOWERSCOUT_IMAGE=towerscout:local`
- stale CA bundle overrides
- other package-managed `TOWERSCOUT_*` values that should come from the package

### Validation for that fix

The fix has focused automated coverage and passed locally:

- `tests/unit/test_task_074_bootstrap.py`
- `tests/unit/test_import_assets_script.py`
- `tests/unit/test_release_package_script.py`
- `tests/unit/test_task_081_runtime_hardening.py`

## Why Final Release Asset Publication Should Pause

Publishing final GitHub Release assets under the existing `v0.1.0` identity would be risky because the release story is now split across two states:

### State A: already public

- source tag `v0.1.0`
- GHCR image tags `v0.1.0-cpu` and `v0.1.0-cuda121`

### State B: locally validated after discovery/fix

- package-launcher hardening in source
- focused regression tests proving the fix
- validated package-launch behavior that relies on that fix being present

If assets are published now under `v0.1.0` without an explicit decision, the release could imply that the public tag/source/image identity already includes behavior that was only fixed afterward.

## Recommendation

### Recommended path: do **not** publish final assets under the current `v0.1.0`

Preferred next step:

1. Commit the launcher hardening fix and its regression test.
2. Choose a **new** release identifier rather than mutating the meaning of `v0.1.0` after publication.
3. Rebuild the release images and control packages from that fixed source state.
4. Re-run the bounded validation sequence for that new identifier.
5. Publish GitHub Release assets only after the fixed source, published image tags, and package contents all line up.

### Preferred versioning choice

Use a follow-on patch release identifier, preferably `v0.1.1`, unless the release owner explicitly wants a different stable naming scheme.

Rationale:

- avoids rewriting the meaning of a public tag
- preserves an honest provenance trail
- keeps the fix visible in history
- reduces future confusion during handoff to `cdcai`

## Alternative Paths

### Option A: Retag/rebuild `v0.1.0`

Not recommended.

This would require intentionally redefining what the already-pushed public tag means, and it would complicate trust in the source/image/package record.

### Option B: Publish assets under current `v0.1.0` anyway

Not recommended.

This would leave the public release identity ambiguous and could publish assets whose trusted behavior depends on a fix not represented in the current tagged source.

### Option C: Follow-on stable release (`v0.1.1` preferred)

Recommended.

This is the cleanest path operationally and historically.

## Recommendation On User Safety

Based on today's evidence, there is **not** enough reason to declare the CPU GHCR image unsafe.

There **is** enough reason to avoid publishing final release assets under the existing `v0.1.0` identity, because the fixed and validated launcher behavior is not yet represented by that public release identity.

That means the safe recommendation is:

- **Do not publish final GitHub Release assets for `v0.1.0` as it stands.**
- **Publish a follow-on release built from the fixed source state instead.**
