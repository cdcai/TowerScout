Document Metadata

Applies to: Current V1 package path through the stable v0.1.0 closeout, unless release notes say otherwise.

Last reviewed: 2026-07-08.

Audience: Pilot users and first-line support.

Runtime scope: The CPU Application Package is the normal path. The CUDA 12.1 Application Package, Podman CPU, Docker GPU, and Podman GPU are support-assigned paths after workstation-specific engine, Compose-provider, and NVIDIA validation.

Before You Start

Confirm Windows 11 AMD64, Windows PowerShell, a modern browser, normal outbound internet access, at least 15 GB free disk space for the CPU package, and one valid site/user-owned provider key. 25 GB free is a better target for CUDA validation.

Application Package means the smaller app/control ZIP with scripts, docs, Compose files, and release metadata. There are two variants: cpu for normal/non-GPU use and cuda121 for support-validated NVIDIA GPU workstations. Model & Data Package means the larger asset ZIP, also called the asset bundle, with model weights and ZIP-code data. Both Application Package variants use the same Model & Data Package for this release path.

Docker Desktop with the WSL 2 backend is the primary pilot engine. During Docker Desktop installation, keep the WSL 2 backend selected when prompted, start Docker Desktop from the Windows Start menu, and wait until Docker Desktop reports that it is running.

Docker's current Windows requirements include WSL 2.1.5 or later, 8 GB RAM, and hardware virtualization enabled in BIOS/UEFI. If your workstation is managed by IT, ask your site administrator before installing WSL, Docker Desktop, Podman, or provider credentials.

wsl --status
wsl --list --verbose
docker --version
docker compose version

Expected result: WSL is installed, any listed Linux distribution uses version 2, and Docker commands print version information while Docker Desktop is running.

Podman is a qualified package-runtime option only when support tells you to use it and the workstation already has a running Podman machine plus an approved non-Docker-Desktop Compose provider. Podman GPU also requires an NVIDIA GPU, current Windows NVIDIA drivers, WSL2 Podman, and NVIDIA CDI validation.

You do not need Git, Python, Conda, Node.js, VS Code, or a source-code checkout for the normal package path.

Unless support has explicitly assigned you the Podman path, stop here and contact your site administrator or support lead if Docker Desktop is not already installed and approved on your workstation. Also stop if you do not already have a valid restricted provider key.

If both Docker and Podman are installed, the launcher can choose Docker first. If support tells you to use Podman, use -Engine podman consistently on every helper command.

Stop And Contact Support

Stop before continuing if Docker Desktop is not installed, not approved, or cannot start unless support explicitly assigned you the Podman path; WSL is unavailable or shows version 1 without administrator approval to update it; setup reports that a ZIP checksum does not match; asset import reports missing, corrupt, or hash-failed files; TowerScout reports fatal; or provider validation repeatedly fails after you confirm the key is correct. On managed networks, provider validation can fail because the container does not trust the local TLS inspection certificate; support can import the site CA without needing your provider key.

Do not share provider keys, .env, raw logs, raw screenshots, private AOIs, browser network traces, cached provider responses, or exported datasets unless your site has an approved handling procedure.

How To Run Commands

Use Windows PowerShell, not the WSL/Ubuntu terminal, for package commands. Open File Explorer, open the extracted TowerScout package folder, click the address bar, type powershell, and press Enter.

Expected result: a PowerShell window opens with the package folder in the prompt. Paste one command at a time and press Enter. Commands that start with .\ run scripts from that folder.

Get The Release Files

Open https://github.com/J-Schulein/TowerScout/releases in your browser, then open the exact release that support told you to use. If support provides a direct release URL, use that link.

In the release Assets section, download one Application Package variant and the shared Model & Data Package. Most browsers save downloaded files to your Windows Downloads folder. After the downloads finish, create a new empty working folder such as C:\Users\<you>\Documents\TowerScoutUAT, then copy the four downloaded TowerScout files from Downloads into that working folder.

Normal users download the CPU Application Package ZIP (towerscout-<release-version>-cpu.zip), its checksum, the shared Model & Data Package ZIP, and the asset checksum from the same release. Use the CUDA Application Package (towerscout-<release-version>-cuda121.zip) only when support assigns GPU validation. Keep the four files together in TowerScoutUAT. For the normal setup path, extract only the Application Package ZIP and leave the Model & Data Package ZIP plus both .sha256 files beside the extracted folder.

Do not use the green GitHub Code button or GitHub's automatic Source code (zip) or Source code (tar.gz) downloads for normal pilot setup.

The release version must match between the Application Package and the Model & Data Package. If the versions differ, stop and download the matching files from the same GitHub release.

Confirm The Release Files Match

Before extracting anything, confirm the folder contains exactly one Application Package ZIP and checksum, plus the shared Model & Data Package ZIP and checksum from the same release. The Application Package is usually the -cpu variant. If support assigned GPU validation, replace it with the matching -cuda121 variant. Do not keep both variants in the same UAT folder unless support asks you to compare them.

Setup verifies the checksum sidecars during first run. If support asks for manual checksum evidence, use the package guide for the detailed Get-FileHash or certutil commands.

Extract The Application Package

In the TowerScoutUAT folder, extract only the Application Package ZIP. Most Windows ZIP tools will create C:\Users\<you>\Documents\TowerScoutUAT\towerscout-<release-version>-cpu for the normal package. After extraction, TowerScoutUAT should contain the four downloaded files plus one extracted package folder.

Do not extract the Model & Data Package ZIP for the normal setup path. The extracted Application Package folder should contain setup-towerscout.cmd, bootstrap.cmd, start.bat, Compose files, scripts\, docs\, and an empty assets\ folder. Do not put the Model & Data Package ZIP inside assets\.

Run TowerScout Setup

Open PowerShell in the extracted application folder that contains setup-towerscout.cmd, then run:

Before running setup, confirm Docker Desktop is open and running. If support assigned the Podman path, confirm the Podman machine is running and the Compose provider is available. For Docker GPU setup, see the optional Docker GPU track below for the GPU setup command.

.\setup-towerscout.cmd

Setup checks disk space, port availability, Docker or Podman readiness, Compose availability, release metadata, checksum sidecars, and asset ZIP layout before importing assets and launching TowerScout. It finds the Model & Data Package ZIP in the extracted application folder or parent TowerScoutUAT folder.

If setup reports that more than one Model & Data Package ZIP was found, move old TowerScout ZIPs out of the folder and run setup again. If support asks for an explicit ZIP path, use the exact Model & Data Package filename:

.\setup-towerscout.cmd -AssetZip C:\Users\<you>\Documents\TowerScoutUAT\towerscout-<release-version>-assets-<asset-version>.zip

Expected result: PowerShell prints TowerScout setup, reports prerequisite checks, verifies checksums, imports valid assets with hash verification, starts TowerScout, and opens http://localhost:5000. If the browser does not open, leave PowerShell open and manually open that URL.

TowerScout setup
[OK] Engine docker is available
[OK] Compose is available
[OK] Model & Data Package checksum matched
[OK] Asset import completed with hash verification
[OK] TowerScout responded at http://localhost:5000
readiness: setup_required

setup_required is normal before provider setup is complete. After provider setup and asset import are complete, readiness should become ready.

The first launch may download the TowerScout container image from GHCR. This can take several minutes. Keep the PowerShell window open while Docker downloads and starts the image.

If TowerScout finds an older UAT container from a previous session, setup starts a fresh container while keeping saved setup, imported assets, and support logs in named volumes.

If support tells you to validate Podman CPU, run .\setup-towerscout.cmd -Engine podman and reuse that engine value on helper commands. If support tells you to validate Docker GPU behavior, use the CUDA Application Package and run .\setup-towerscout.cmd -Engine docker -Gpu auto or .\setup-towerscout.cmd -Engine docker -Gpu on. If support tells you to validate Podman GPU, confirm the CDI preflight first, then use the CUDA package and run .\setup-towerscout.cmd -Engine podman -Gpu on. The CPU package rejects -Gpu on.

Manual Asset Import Fallback

Use this section only if support tells you not to use setup-towerscout.cmd, or if you already extracted the Model & Data Package manually.

Extract the Model & Data Package ZIP root entries into the package assets\ folder so it contains model_params\, data\, and asset_manifest.v1.json directly inside assets\.

If you see assets\assets\model_params, the files are nested one level too deep. Move the inner model_params, data, and asset_manifest.v1.json entries up one level before importing. If you are unsure, stop and ask support.

.\scripts\import-assets.cmd -Engine docker -Source assets -VerifyHashes -RestartWaitSeconds 180

If TowerScout was started on a non-default port, pass the same port to the asset importer.

.\scripts\import-assets.cmd -Engine docker -Source assets -Port 5001 -VerifyHashes -RestartWaitSeconds 180

The importer uses the selected engine's named volumes. If .env is missing, it initializes that file from the package .env.example before starting the selected container stack. It restarts TowerScout after copying assets so imported model files are available before the first detection run. Expected result: the command finishes without missing/corrupt asset errors and waits for TowerScout after restart.

GPU Boundary

The default launch is CPU-safe. Optional GPU launch is support-assigned and should be used only with the CUDA Application Package after workstation-specific NVIDIA container validation for the selected engine.

.\start.bat -Engine docker -Gpu auto
.\start.bat -Engine docker -Gpu on
.\start.bat -Engine podman -Gpu on

The CPU package rejects -Gpu on. The CUDA package still fails closed unless readiness reports selected_device=cuda. For Podman GPU, support must validate the non-Docker-Desktop Compose provider and NVIDIA CDI path before launch. The RC5 validated path used Podman 5.8.2 on Windows 11 WSL2, standalone Docker Compose v5.1.4 selected through PODMAN_COMPOSE_PROVIDER, and NVIDIA CDI device nvidia.com/gpu=all.

Complete Setup

Use Setup Wizard or Settings to configure one valid Google Maps or Azure Maps key. Browser map SDK keys are client-visible, so the package expects site/user-owned restricted keys.

If Google or Azure validation fails even though the key is correct, and support sees CERTIFICATE_VERIFY_FAILED in container logs, the Setup Wizard or Settings may show a suggested dry-run command that preserves the active engine and GPU mode. Support should run the guided TLS repair helper for the selected runtime, review the local support-sensitive dry-run output, then run the generated apply command and restart TowerScout. For Azure validation failures, support may use -Provider azure. The helper stores the combined CA bundle in the selected engine's config volume and updates local .env so future starts use that bundle automatically.

Confirm Success

.\scripts\status.cmd -Engine docker

Readiness should become ready after provider setup and required assets are present. For a smoke check, support should provide the fixture before UAT starts: provider, public/non-sensitive location name, expected tile range, and whether zero detections is acceptable. Do not choose a private investigation AOI for the first smoke test. Estimate tiles first, keep the run small, then select Find towers. The default pilot Azure smoke fixture is about 8 tiles.

The UAT package defaults to a pilot guard of 100 tiles. If TowerScout reports that the selected area exceeds the current pilot limit, reduce the search area or contact support before running a larger validation.

Expected result: the detection workflow completes without crashing. For the default pilot Azure fixture, expect a non-zero tower result. Exact counts may vary, but zero towers, no review-panel update, or a crash should be reported as BLOCKED or FAIL. For any future support-approved fixture, follow the zero-detection rule support provided for that fixture.

Stop Or Restart

.\scripts\stop.cmd -Engine docker
.\start.bat -Engine docker -Gpu off

Provider setup and imported assets are stored in named volumes and should survive container restarts. Always use the same -Engine value you used during setup. Docker Desktop and Podman use separate local storage, so switching engines can make setup or imported assets appear to be missing.

TowerScout treats a healthy container that is less than 12 hours old as the current UAT session. If a container is stopped, unhealthy, or older than 12 hours, the launcher starts a fresh container and keeps named volumes by default. Support can change the session lifetime with -SessionMaxHours when a longer validation session is approved.

If Something Fails

.\scripts\status.cmd -Engine docker
.\scripts\logs.cmd -Engine docker -Tail 200

Send only support-requested, reviewed/redacted excerpts from log output. Do not send raw logs unless your site has an approved handling procedure.

For fuller troubleshooting and support details, open the package guide at /docs/package-guide.md.

For package/image metadata, support may ask you to copy the package folder name and the contents of IMAGE.txt.

Get-Content .\IMAGE.txt

If PowerShell says a command is not recognized, confirm the prompt is open in the extracted TowerScout package folder and that the command starts with .\. If Docker commands are not recognized, open Docker Desktop from the Start menu and wait until it reports that it is running.

Do not share provider keys, .env, raw screenshots, browser traces, raw logs, datasets, or sensitive AOIs unless your site has approved handling.
